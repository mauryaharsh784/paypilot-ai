# PayPilot AI

Autonomous AI commerce and smart payments platform for the "Build What's Next with PayPal and AI" hackathon. Built by Neha Gupta and Harsh Vardhan Maurya.
Users describe what they need; five tool-calling agents research, compare, budget and prepare a cart; the user approves; PayPal Sandbox takes the payment; the server verifies it.

**Stack:** React 18, TypeScript, Vite, Tailwind, React Router, Zustand, Recharts, Framer Motion (installed), Lucide, `@paypal/react-paypal-js` · Node, Express, TypeScript, MongoDB/Mongoose, JWT in HTTP-only cookies · Gemini or OpenAI function calling · PayPal Orders API v2 + Webhooks.

## Why PayPal, and what makes the payment flow safe
PayPilot uses the PayPal **Orders API v2** (create, capture, get) and **verified webhooks**. The AI agents can only *prepare* an order. A payment starts only after the user approves, and an order becomes paid only when the server has verified the capture (status, amount, currency, order id) or a signature-verified webhook. Retries, double clicks and duplicate webhooks cannot create a second payment. Details: [docs/PAYPAL.md](docs/PAYPAL.md) and [docs/SUBMISSION.md](docs/SUBMISSION.md).

## Judges: quick start (about 5 minutes)
1. `cd server && cp .env.example .env`, set `JWT_SECRET` (any long random string) and optionally PayPal Sandbox keys and an AI key. A MongoDB is required (local, or an Atlas URI in `MONGODB_URI`; **MongoDB 4.2+**).
2. `npm install && npm run seed && npm run dev` (API on :4000). In another terminal: `cd client && npm install && npm run dev` (web on :5173).
3. Sign in as the seeded admin (`ADMIN_EMAIL` / `ADMIN_PASSWORD` from `.env`) or register a user.
4. Without PayPal keys everything works except paying: checkout stops with a clear "PayPal sandbox credentials are not set" error. It never fakes a payment. Without an AI key the assistant runs in labelled **rules mode**.

## Product images
Every demo product has its own locally stored SVG illustration in `client/public/products/<slug>.svg` (plus per-category fallbacks `_<category>.svg`). They are **stylised illustrations, not photographs**, generated by `client/scripts/generate-product-images.mjs` (`node scripts/generate-product-images.mjs` to regenerate). They ship with the repo, so they never depend on a third-party image host.
`ProductImage` (`client/src/components/ProductImage.tsx`) shows a shimmer while loading and falls back to the category illustration, then to a category icon. Products can carry an optional `image` (`/products/x.jpg` or an `https://` URL), settable in Admin. When it is empty the client uses `public/products/<slug>.svg`, then the category illustration. The cart, checkout and order history all show the product image: new orders store `slug`, `category` and `image` with each item, and older orders are filled in from the catalog when they are read. To use real photos, drop optimised files into `public/products/` and set `image` (or reuse the same file names).

## Run locally

Requirements: Node 18.18+, a MongoDB (local or Atlas), a PayPal developer account.

```bash
# 1. API
cd server
cp .env.example .env        # fill in JWT_SECRET, PayPal sandbox keys, optional AI key
npm install
npm run seed                # sample catalog + admin user (ADMIN_EMAIL / ADMIN_PASSWORD)
npm run dev                 # http://localhost:4000

# 2. Web (new terminal)
cd client
npm install
npm run dev                 # http://localhost:5173  (proxies /api to :4000)
```

### PayPal Sandbox setup
1. developer.paypal.com > Apps & Credentials > Sandbox > create an app. Copy Client ID and Secret into `server/.env`.
2. Create a **webhook** on that app pointing to `https://<public-api-host>/api/webhooks/paypal` (use ngrok locally, or your Render URL). Subscribe to: `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.DENIED`, `PAYMENT.CAPTURE.DECLINED`, `PAYMENT.CAPTURE.REFUNDED`. Put the Webhook ID in `PAYPAL_WEBHOOK_ID`.
3. Pay with a Sandbox *personal* (buyer) account from Sandbox > Accounts.

### AI setup
Set `GEMINI_API_KEY` (or `OPENAI_API_KEY`). Model names are env vars (`GEMINI_MODEL`, `OPENAI_MODEL`); check they are current for your account.
With no key the agents run in **rules mode**: same tools, same validation, deterministic text. The UI shows which mode produced each reply and an "Agent activity" trace of tools called.

## How it works

**Agents** (`server/src/agents.ts`): Shopping, Research, Comparison, Budget, Payment. Each has its own tool list and a zod-validated JSON output. Tools (`tools.ts`) read the real database. Research ids are checked against the DB and the budget is enforced as a hard filter, so a model cannot invent a product. Comparison and Budget run in parallel; numbers shown in the UI come from backend tools, not model text.

**Payment flow** (`payments.ts`, `routes.ts`):
1. Cart or assistant → `POST /api/checkout/prepare` creates an order (server totals, server FX conversion). Status `awaiting_approval`.
2. User ticks approval → `POST /api/orders/:id/approve {confirm:true}`. The server re-prices from the live catalog (409 `PRICE_CHANGED` if anything moved), then creates the PayPal order with a deterministic `PayPal-Request-Id` that changes whenever a new PayPal order is needed for the same order (PayPal replays the old response for a reused id).
3. PayPal Buttons approve client-side → `POST /api/orders/:id/capture`. The server takes a per-order lock, captures, and checks status, amount, currency and `custom_id` (required, must equal the order id) against the order before marking it paid.
4. The webhook (`/api/webhooks/paypal`, raw body) verifies the signature via PayPal's verify API, stores the event id once (finished duplicates are ignored; an event still being processed gets a 409 so PayPal retries; a crashed run is taken over after 2 minutes; failures are deleted so PayPal retries), cross-checks the capture's PayPal order id, and reaches the same `markPaid`, which is atomic and idempotent.
5. If a webhook never arrives, an admin can call `POST /api/admin/orders/:id/sync`. It reads the order from PayPal and runs the same verification and `markPaid`.
6. Client-reported cancel/error events are only logged. They never change payment state.

**Spec endpoint map:** the spec's REST paths are all served. Some are aliases of the original routes: `/ai/chat` and `/ai/agent/run` = `/assistant/message`; `/paypal/create-order` = `/orders/:id/approve`; `/paypal/capture-order` = `/orders/:id/capture`; `/paypal/webhook` = `/webhooks/paypal`; `/preferences` (GET, PATCH); `/price-watch` (GET, POST, DELETE); `POST /wishlist`; `GET /products/search`; `POST /products/compare`; `/admin/analytics`, `/admin/users`, `/admin/ai-activity`.

**Behaviour notes:** paying removes only the ordered items from the cart. Checkouts left unpaid for 24 hours are marked cancelled (expired) the next time the user opens their orders; a late PayPal webhook can still mark such an order paid. If stock is too low at payment time the order is still paid, the capture transaction records `detail.stockShortfall`, and admins get a notification. Repeated client cancel/error events for the same order are logged once per 10 minutes, and that endpoint is rate limited. The Transactions page shows the INR order total next to the USD charge when the two match.

**Security notes:** secrets only in env; no card data touched; bcrypt passwords; JWT in HTTP-only cookie; Helmet; rate limits on auth and chat; zod validation everywhere; agents cannot call PayPal, they can only prepare an order.

## Honest limitations
- The catalog is **sample data with fictional brands**. Replace it through the admin dashboard or your own import. The "performance index" spec is a sample value, not a benchmark.
- PayPal rarely settles INR, so the INR catalog is converted to `PAYPAL_CURRENCY` at the fixed `INR_PER_UNIT` rate. Use a live rate source for production.
- Price history contains only real recorded points (seed price, then admin price changes). Alerts fire from those changes.
- Webhooks for a PayPal order other than the one an order currently holds are recorded as `order_mismatch` and never mark the order paid. Money captured that way needs manual review in PayPal.
- Refunds are **not** issued by the app. The assistant gives guidance, and a `PAYMENT.CAPTURE.REFUNDED` webhook is recorded if you refund in PayPal.
- **Verified earlier:** server and client typecheck and build; 76 API checks, 47 mock-PayPal payment checks and 98 acceptance checks passed against a real MongoDB (4.0 with `mongoose@7` in the test environment). Later changes (stricter `custom_id`, per-attempt request ids, webhook in-progress handling, admin sync, product images in orders) have a syntax check only. Re-run all three suites and `npm run typecheck` before submitting.
- **UI verified (headless Chromium, Playwright):** registration, Discover filters/empty state, add to cart, wishlist add/remove, compare, cart quantity and budget, checkout approval gate, assistant (rules mode), all sidebar links, product images (no broken images), no horizontal overflow at 375/768/1024/1440 px on the main pages, mobile drawer.
- **Not verified:** a real PayPal Sandbox payment and webhook delivery (the PayPal button was never rendered with real credentials), any real LLM provider (only rules mode was exercised), pages with populated order/transaction history in the browser (the table layouts compile and the empty states were tested, but a paid order was only exercised through the API suites), and Mongoose 8 against MongoDB 4.2+. Do these before submitting:
  - [ ] One real Sandbox checkout reaches Paid
  - [ ] One real webhook shows in Admin > Overview > Webhook log
  - [ ] Assistant answers with your Gemini/OpenAI key
  - [ ] Click through Dashboard, Cart, Admin tabs

## Deploy
- **MongoDB Atlas:** create a cluster, set `MONGODB_URI`, run `npm run seed` once with it.
- **Render (API):** root `server`, build `npm install && npm run build`, start `npm start`. Set all `server/.env.example` variables, `NODE_ENV=production`, `CLIENT_URL=https://<your-vercel-domain>`.
- **Vercel (web):** root `client`. Edit `client/vercel.json` and replace `YOUR-RENDER-SERVICE` with your Render host. The rewrite keeps `/api` same-origin so the auth cookie stays first-party. Then register the webhook with the Render URL.
